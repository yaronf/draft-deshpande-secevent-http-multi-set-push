# Document Shepherd Write-Up for Individual Documents

*This version is dated 4 July 2022.*

Title: Push-Based Delivery For Multiple Security Event Tokens (SET) Using HTTP
Shepherd: Yaron Sheffer <yaronf.ietf@gmail.com>
Responsible AD: Deb Cooley
Intended status: Proposed Standard
Write-up date: 2026-08-25

## Document History

1. Was the document considered in any WG, and if so, why was it not adopted as a
   work item there?

   Yes. The work was discussed in the context of the former Security Events
   (SECEVENT) Working Group and on the id-event mailing list. SECEVENT has been
   concluded for some time, and there was insufficient community energy to
   recharter the WG. The document therefore progressed as an AD-sponsored
   individual submission in the Security Area under Deb Cooley. Interest
   continues in the former SECEVENT community and in the OpenID Foundation
   Shared Signals Framework (SSF).

2. Was there controversy about particular points that caused the WG to not adopt
   the document?

   No. Non-adoption reflects the closed status of SECEVENT and lack of energy
   to recharter, not controversy over the technical content.

3. Has anyone threatened an appeal or otherwise indicated extreme discontent? If
   so, please summarize the areas of conflict in separate email messages to the
   responsible Area Director. (It should be in a separate email because this
   questionnaire is publicly available.)

   No.

4. For protocol documents, are there existing implementations of the contents of
   the document? Have a significant number of potential implementers indicated
   plans to implement? Are any existing implementations reported somewhere,
   either in the document itself (as RFC 7942 recommends) or elsewhere
   (where)?

   There are no confirmed implementations of this specification at this time.
   Implementers of RFC 8935 (single-SET push delivery) have provided feedback on
   the draft. The authors plan to incorporate this batched delivery mechanism
   into the OpenID Shared Signals Framework
   (https://openid.net/specs/openid-sharedsignals-framework-1_0-final.html) to
   encourage broader implementation attention. No RFC 7942 implementation status
   section is present in the document.

## Additional Reviews

1. Do the contents of this document closely interact with technologies in other
   IETF working groups or external organizations, and would it therefore benefit
   from their review? Have those reviews occurred? If yes, describe which
   reviews took place.

   Yes. The document extends RFC 8935 SET push delivery and uses HTTP extensively,
   so early directorate reviews were requested and completed:

   - HTTP Directorate early review of -00 by Darrel Miller ("On the Right Track"):
     https://datatracker.ietf.org/doc/review-deshpande-secevent-http-multi-set-push-00-httpdir-early-miller-2025-11-23/
     also posted to ietf-http-wg@w3.org:
     https://lists.w3.org/Archives/Public/ietf-http-wg/2025OctDec/0216.html
   - Genart early review of -00 by Russ Housley
   - Secdir early review of -00 by Scott G. Kelly

   Shepherd review comments and the HTTPDir follow-ups (including media type
   registration, RFC 9110 citations, 202 "accepting" wording, RFC 9457 problem
   details for request-level failures, and clarification of error handling) were
   addressed in subsequent revisions culminating in -03.

   Externally, the work is relevant to the OpenID Foundation Shared Signals
   Framework community, which builds on SECEVENT SET delivery.

   The document registers the media type application/secevents+json. Media-type

## Document Shepherd Checks

1. Based on the shepherd's review of the document, is it their opinion that this
   document is needed, clearly written, complete, correctly designed, and ready
   to be handed off to the responsible Area Director?

   Yes. The document fills a practical gap relative to RFC 8935 by defining
   efficient batched push delivery of multiple SETs in a single HTTP request,
   with clear acknowledgement and error semantics. After shepherd review and
   incorporation of early directorate feedback through -03, the shepherd
   considers the document ready for AD hand-off / further IETF process.

2. Several IETF Areas have assembled lists of common issues that their
   reviewers encounter. For which areas have such issues been identified
   and addressed? For which does this still need to happen in subsequent
   reviews?

   Security Area and HTTP-related issues were substantially addressed via Secdir,
   HTTPDir, Genart early reviews, AD feedback, and shepherd review (including
   TLS reference update to RFC 9846, request-size limits, disclosure guidance in
   setErrs, Recipient terminology consistency, and HTTP semantics alignment with
   RFC 9110 / RFC 9457). Further review during IETF Last Call remains appropriate.

3. What type of RFC publication is being requested on the IETF stream (Best
   Current Practice, Proposed Standard, Internet Standard,
   Informational, Experimental or Historic)? Why is this the proper type
   of RFC? Do all Datatracker state attributes correctly reflect this intent?

   Proposed Standard. This is an interoperable wire protocol for SET delivery
   that extends the Standards Track RFC 8935 model. Datatracker intended status
   and the draft's "Standards Track" header correctly reflect this intent.
   Consensus boilerplate is present.
